# Анализ системы компании и C4-диаграммы в контексте планирования трейсинга.

Чтобы команда могла отслеживать путь заказа от начала до конца, необходимо внедрить распределённый трейсинг (distributed tracing), который позволит:

- Видеть весь путь заказа по системе.
- Определять, на каком этапе он завис или завершился с ошибкой.
- Измерять время обработки на каждом этапе.
- Обнаруживать потерянные сообщения в очередях.

| Компонент | Тип | Почему нужен трейсинг |
|----------|-----|------------------------|
| `Internet Shop` | Frontend | Чтобы привязать начало заказа к пользователю и сгенерировать `trace_id` |
| `Shop API` | Backend (Spring Boot) | Ключевой точка входа. Должен генерировать `trace_id` и передавать его дальше |
| `3d files storage` | External service | Нужно логировать успешность загрузки/чтения 3D-файла с `trace_id` |
| `Shop DB` | Database | Логировать успешность сохранения заказа (можно через обёртку или логи приложения) |
| `Messages Queue` (RabbitMQ) | Message broker | Все сообщения должны содержать `trace_id` в заголовке |
| `CRM API` | Backend (Spring Boot) | Должен продолжать трейс при получении сообщения из очереди |
| `CRM` | Frontend | Показывать статус заказа с привязкой к трейсу |
| `MES API` | Backend (C#) | Самый критичный сервис: расчёт стоимости, назначение оператора |
| `MES` | Frontend | Оператор должен видеть, какой заказ он взял, с привязкой к трейсу |
| `MES DB` | Database | Фиксировать обновление статуса с `trace_id` |
| `API user` | External system | При прямом вызове MES API — `trace_id` должен быть в запросе или сгенерирован |

## Список данных для включения в трейсинг

| № | Данные | Источник | Зачем нужно |
|----|--------|---------|------------|
| 1 | `trace_id` | Генерируется на входе (Internet Shop или API user) | Уникальный идентификатор всего процесса обработки заказа |
| 2 | `parent_span_id` | Предыдущий сервис | Строит дерево вызовов (например, Shop API → RabbitMQ → CRM API) |
| 3 | `order_id` | Shop API / CRM API | Привязка трейса к конкретному заказу |
| 4 | `user_id` | Internet Shop / CRM | Понимание, кто создал заказ (клиент или менеджер) |
| 6 | `source` (web, api) | Internet Shop, API user | Понимать источник |
| 7 | `3d_model_file_id` | Shop API, MES API | Отслеживание обработки конкретной 3D-модели |
| 10 | `start_time` (время создания заказа) | Internet Shop | Время начала обработки |
| 11 | `status` на каждом этапе | Все сервисы | Текущий статус |
| 13 | `endpoint` или `operation` | API-сервисы | Какая операция выполнялась: `/api/orders`, `/calculate-cost` |
| 14 | `error_code` | Все сервисы | Код ошибки при сбое (500, 400, timeout) |
| 15 | `error_message` | При ошибках | Подробное описание |
| 18 | `message_id` | RabbitMQ | Уникальный ID сообщения в очереди |
| 19 | `timestamp` события | Все сервисы | Время начала и завершения каждого этапа (для измерения задержек) |

# Мотивация

Почему нужно внедрить трейсинг:

- Невозможно понять, на каком этапе завис заказ.
- Нельзя определить, был ли обработан 3D-файл или достиг ли заказ MES.
- Жалобы клиентов и партнеров растут, но некому дать ответ: «Где ваш заказ?»
- Это приводит к потере доверия, срыву контрактов и замедлению роста бизнеса.

После внедрения:

- Команда сможет ввести trace_id или order_id и увидеть всю цепочку обработки.
- Можно будет найти зависшие заказы и понять, на каком этапе произошёл сбой.
- Сократится время расследования инцидентов с часов до минут.
- Повысится доверие со стороны клиентов и операторов.
- Сокращение времени на поддержку
- Поддержка масштабирования


| № | Метрика | Тип | Как трейсинг улучшит метрику |
|----|--------|------|-------------------------------|
| 1 | **Среднее время обработки заказа (от создания до появления в MES)** | Бизнес-метрика | Трейсинг позволит точно измерить время на каждом этапе и выявить узкие места (например, долгая валидация 3D-файла). |
| 2 | **Количество заказов, зависших в RabbitMQ (backlog)** | Техническая | Связь сообщений с `trace_id` покажет, какие заказы не были обработаны и почему (ошибка потребителя, таймаут). |
| 3 | **Доля заказов, попавших в dead-letter queue** | Техническая | Трейсинг поможет быстро находить и анализировать причины падения сообщений (ошибки десериализации, невалидные данные). |
| 4 | **Время отклика для внешних API-пользователей** | Бизнес-метрика | Можно будет измерить полное время ответа, включая обработку в MES, и гарантировать SLA. |
| 5 | **Количество "невидимых" заказов (нет в MES, но есть в CRM)** | Бизнес-метрика | Трейсинг покажет, где оборвалась цепочка — в очереди, в потребителе или при сохранении в БД. |

# Компромиссы

## Высокая нагрузка на 3D-обработку: трейсинг не ускорит расчёт

Расчёт стоимости в MES зависит от сложности 3D-модели и может занимать до 30 минут. Трейсинг покажет, что процесс долгий, но не ускорит его. 

Трейсинг фиксирует проблему, но не решает её.
Команда может видеть, что calculate-cost занял 28 минут, но не сможет изменить производительность алгоритма без переписывания логики.
Решение: кэширование, предварительная валидация, масштабирование — но это не связано с трейсингом.

> Итог: трейсинг полезен для диагностики, но не заменяет оптимизацию бизнес-логики. 

## Ограниченный бюджет и ресурсы команды

У компании всего три окружения (dev, release, prod), релизы задерживаются, QA тестирует вручную. Внедрение трейсинга: 

- Требует изменений в каждом сервисе.
- Нагружает разработчиков.
- Может вызвать новые баги.

Трейсинг отодвигает другие задачи (например, исправление ошибок валидации 3D-файлов).
Если команда перегружена, трейсинг может усугубить ситуацию.
Решение: внедрять поэтапно, начиная с критичных сервисов (Shop API, MES API).

## Низкая ценность для простых сценариев

Для простых заказов (стандартные украшения без 3D-моделей) трейсинг не даёт значимой выгоды. 

- Процесс короткий и прозрачный.
- Жалоб от клиентов почти нет.

Трата ресурсов на трейсинг низкоуровневых сценариев, где он не нужен.
## Legacy-интеграции без trace_id

Невозможно связать с внешним миром

# Аспекты безопасности

Внедрение системы трейсинга (Jaeger, Grafana, Prometheus) приносит  пользу, но также расширяет поверхность атаки, так как трейсы содержат:

- Идентификаторы заказов (order_id)
- ID пользователей (user_id, operator_id)
- Время и статус обработки
- Возможные ошибки с деталями валидации

Это чувствительные данные, и их доступность должна быть строго контролируемой.

**Комплекс мер по обеспечению безопасности** системы трейсинга внутри компании и снаружи.

### Интеграция Grafana и Jaeger с внутренней системой аутентификации 

Реализация: 

- Только сотрудники с активной учётной записью могут войти.
- Доступ к интерфейсам — через единое окно входа (SSO).
- Поддержка MFA (двухфакторная аутентификация) для администраторов.

Пример:
«Войти в Grafana смогут только сотрудники с ролью Поддержка, DevOps, SRE или Разработчик».

###  Контроль доступа по ролям (RBAC)

| Роль | Доступ к системе трейсинга | Разрешённые действия |
|------|----------------------------|----------------------|
| **Поддержка** | Только чтение | Просмотр трейсов по `trace_id` или `order_id`. Поиск в интерфейсе Jaeger/Grafana. |
| **Разработчик** | Полный доступ к данным | Просмотр, анализ трейсов, метрик и логов. Создание и редактирование дашбордов в Grafana. |
| **DevOps / SRE** | Полный доступ + управление | Всё, что у разработчика, плюс настройка алертов, управление экспортерами и OTel Collector. |
| **Администратор** | Полный доступ + управление пользователями | Управление ролями, добавление/удаление пользователей, настройка аутентификации (SSO, MFA). |
| **API-пользователь (внешний)** | Нет доступа к UI | Только через защищённый API (`/api/orders/{id}/status`) с API-ключом. Никакого доступа к Jaeger/Grafana. |

### Сетевая безопасность и изоляция

- Добавить доступ к мониторингу через внутренний vpn или корпоративную сеть

### Защита данных в передаче и хранении

- Шифрование транспорта (TLS)

###  Аудит и логирование доступа

- логировать вхожы в Grafana и Jaeger
