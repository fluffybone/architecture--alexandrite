# Анализ системы компании и C4-диаграммы в контексте планирования мониторинга.

Системы для которых можно добавить мониторинг

- Internet Shop (Vue, TypeScript, Three.js) — клиентский веб-интерфейс.
- Shop API (Spring Boot) — обрабатывает заказы, взаимодействует с 3D-моделями.
- CRM (Vue, TypeScript) — интерфейс для продавцов.
- CRM API (Spring Boot) — бэкенд CRM.
- MES (React, TypeScript) — интерфейс для операторов производства.
- MES API (C#) — распределяет заказы, рассчитывает стоимость.
- Messages Queue (RabbitMQ) — шина сообщений.
- Базы данных: Shop DB и MES DB (PostgreSQL).
- 3d files storage — S3-совместимое хранилище 3D-моделей.

> Мониторинг должен охватывать здоровье, производительность, доступность и целостность данных на всех уровнях.

# Мотивация

Необходимо добавить мониторинг:

- Для сохранения репутации и прибыли компании. В настоящее время компания теряет клиентов из-за того, что заказы не доходят до адресатов.
- Отсутствует возможность оперативно выявлять ошибки, связанные с заказами.
- Компания узнает о таких инцидентах только от клиентов, что негативно сказывается на репутации и ведет к потере доверия с их стороны.
- Разработчики вынуждены тратить значительное время на выявление места возникновения сбоя и причин, по которым заказ не был отправлен в производство.
- Также мониторинг стоит добавить для прогнозирования нагрузки, чтобы вовремя обеспечить работу систем без сбоя.
- При добавлении мониторинга безопасности, мы сможем проанализировать попытки взлома, непровамерное получение доступа к информации компании, утечки данных.
- Нет единой картины системы, есть отдельные сервисы, связи между ними нет, нет понимания, как работает система в целом. В идеале хочется видеть состояние каждого контейнера, отображать потоки данных (например, заказ прошёл в MES?), создать единый дашборд для всех команд (разработка, поддержка, менеджмент).
- Нет метрик ошибок, сколько их бало, как часто, в каком окружении.

После введения мониторинга ожидается:

- Снижение числа жалоб — за счёт прозрачности.
- Ускорение обработки заказов — за счёт выявления узких мест.
- Повышение доверия B2B-партнёров — API будет стабильным.
- Рост производительности операторов — они увидят новые заказы.
- Ускорение релизов — команда будет принимать решения на данных

# Выбор подхода к мониторингу

| подходы к мониторингу           | системы    | почему        | 
|---------------------------------|------------|---------------|
| RED                             |Messages Queue (RabbitMQ), 3D files storage  |RED потому что важно понимать поток событий(Сколько заказов потерялось в очереди?Сколько времени уходит на обработку 3D-модели? Справляется ли система с нагрузкой?)     |
| USE                             |Shop DB, MES DB, 3D files storage     | контролировать инфраструктуру и предотвращать сбои(Почему тормозит БД? Не хватает ли памяти на MES API? Диск перегружен?)          |
| Четыре золотых сигнала от Google|Internet Shop, CRM, MES, MES API,  CRM API  | Данный метод фокусируется на пользовательском опыте и бизнес-метриках, что критично для клиентов и работников компании (Почему заказ не пришёл? Почему долго грузится MES? Сколько времени обрабатывается мой 3D-файл?)|

- Четыре золотых сигнала — чтобы видеть проблему глазами клиента.
- RED — чтобы понимать, что происходит в сервисах и очередях.
- USE — чтобы контролировать инфраструктуру и предотвращать сбои.

# Какие метрики и в каких частях системы будем отслеживать

| № | Метрика | Зачем нужна | Ярлыки (labels) |
|----|--------|-------------|------------------|
| 1 | `Number of dead-letter-exchange letters in RabbitMQ` | Показывает количество сообщений, которые не были обработаны. Критично: заказы теряются, клиенты не получают ответ. | `queue`, `exchange`, `error_reason` |
| 2 | `Number of message in flight in RabbitMQ` | Отражает количество сообщений, взятых в обработку, но ещё не подтверждённых. Высокое значение — признак зависания или сбоя потребителя (например, MES API). | `queue`, `consumer` |
| 3 | `Number of requests (RPS) for internet shop API` | Основной индикатор нагрузки от пользователей. Рост = больше заказов, требуется масштабирование. | `endpoint`, `method` |
| 4 | `Number of requests (RPS) for CRM API` | Показывает нагрузку от менеджеров и внешних API-пользователей. Важно после открытия B2B-доступа. | `endpoint`, `source` (web/api) |
| 5 | `Number of requests (RPS) for MES API` | Ключевая метрика: расчёт стоимости — самая ресурсоёмкая операция. Рост RPS = риск перегрузки. | `endpoint`, `operation_type` (calculate, assign) |
| 6 | `Number of requests (RPS) per user for internet shop API` | Позволяет выявить аномалии: боты, ошибки, активность одного клиента. Полезно для анализа UX. | `user_id`, `session_id` |
| 7 | `Number of requests (RPS) per user for CRM API` | Контроль активности менеджеров. Аномалии могут указывать на ошибки ввода или сбои. | `user_id`, `role` (manager, admin) |
| 8 | `Number of requests (RPS) per user for MES API` | Операторы получают вознаграждение за заказы. Нужно видеть, кто активен, кто не работает. | `operator_id`, `role` |
| 9 | `CPU % for shop API` | Высокая загрузка CPU может указывать на нехватку ресурсов или утечки в Spring Boot-приложении. | `instance`, `region` |
| 10 | `CPU % for CRM API` | Spring Boot может потреблять много CPU при сериализации данных или работе с сессиями. | `instance` |
| 11 | `CPU % for MES API` | C#-приложение при расчёте сложных 3D-моделей может сильно нагружать CPU. | `instance`, `model_complexity` |
| 12 | `Memory Utilisation for CRM API` | Утечки памяти при долгих сессиях или кэшировании данных. | `instance` |
| 13 | `Memory Utilisation for MES API` | Обработка 3D-моделей требует много памяти. . | `instance`, `operation_type` |
| 14 | `Memory Utilisation for shop db instance` | PostgreSQL использует память для кэширования. Нехватка — причина медленных запросов. | `database`, `instance` |
| 15 | `Memory Utilisation for MES db instance` | Самая нагруженная БД. Медленная работа MES часто из-за нехватки памяти. | `database`, `instance` |
| 16 | `Number of connections for shop db instance` | Ограничение PostgreSQL (~100 подключений). Переполнение = сбои в API. | `database`, `user`, `application` |
| 17 | `Number of connections for MES db instance` | Самая критичная БД. Рост подключений — признак утечки в пуле. | `database`, `operator_id`, `application` |
| 18 | `Response time (latency) for shop API` | Пользователи жалуются на задержки. Нужно измерять время ответа на ключевые эндпоинты. | `endpoint`, `request_size`, `model_complexity` |

# План действий

| Задача | Описание | Технологии |
|-------|--------|----------|
| Создать инстанс time-series базы данных | Развернуть отказоустойчивый инстанс для хранения метрик. | Prometheus, VictoriaMetrics, Yandex Managed Service for Prometheus |
| Настроить долговременное хранение метрик | Обеспечить хранение метрик не менее чем за 6 месяцев. | Thanos  или интеграция с S3-совместимым хранилищем |
| Развернуть централизованную систему логирования | Собрать логи со всех сервисов в единое хранилище. | Elasticsearch |
| Развернуть систему трассировки (tracing) | Внедрить distributed tracing для отслеживания жизненного цикла заказа. | Jaeger |
| Настроить дашборды и алертинг | Установить и настроить систему визуализации и уведомлений. | Grafana, интеграции с Telegram |
