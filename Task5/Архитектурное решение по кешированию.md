# Анализ диаграммы системы и её описания

Стоит закешиировать информацию, которая редко меняется, и к которой часто обращаются, но актуальность может быть с погрешностью в несколько минут

Например:
 - **MES** - списки заказов, результаты фильтрации 
 - расчет 3d моделей
 
 # Мотивация


- **Операторы жалуются**, что интерфейс MES **загружается слишком медленно**, особенно при открытии списка заказов.
- **Клиенты недовольны** тем, что заказы выполняются **значительно дольше обещанных сроков** (3 недели).
- **Нагрузка на систему растёт линейно**, но **производительность не масштабируется** — особенно это заметно в `MES API` и `MES DB`.

| Проблема | Решение через кэширование |
|--------|---------------------------|
| **Долгая загрузка страницы в MES** | Кэширование списка заказов — оператор видит актуальные данные за < 2 секунды |
| **Медленный расчёт стоимости (до 30 минут)** | Кэширование результатов для типовых 3D-моделей — ответ за < 1 секунду |
| **Высокая нагрузка на CPU `MES API`** | Снижение числа тяжёлых вычислений за счёт повторного использования результатов |
| **Рост числа жалоб от клиентов** | Ускорение обработки заказов -> соблюдение сроков |
| **Перегрузка `MES DB`** | Снижение числа запросов к БД за счёт кэширования |

# Предлагаемое решение

Использвать лучше серверное кеширование так как система обрабатывает чувтсвительную информацию, а при использовании клиентского кеширования, кеш может быть скомпрометирован. 

Также  один результат кэшируется один раз и используется всеми, а не кэшируется у каждого клиента отдельно.

Кешем на сервере можно управлять - очищать, реплицировать, масштабировать независимо от клиентов.

 **Cache-Aside** (Redis) подходит для наших сценариев:
1. Кэширование результатов расчёта стоимости.
2. Кэширование списка заказов в `MES`
3. Кеширование фильтрации списков

| Паттерн | Подходит для MES? | Причина |
|--------|-------------------|--------|
| **Cache-Aside** | Да | Простой, эффективный, подходит для тяжёлых вычислений и редких обновлений. Приложение обновляет кеш |
| **Write-Through** | Нет | не решает задачу повторного использования результатов, для системы в приоритете кешировать данные, которые мы читаем. Запись не так часто требуется. Каждое изменение требует синхронной записи в БД, что замедлит обработку заказов. |
| **Refresh-Ahead** |  Нет | Требует прогнозирования, неэффективен при непредсказуемых запросах. Кажется избыточным и требует качественную систему мониторинга |

 Пояснение к диаграмме
**Чтение списка заказов**: (голубые стрелочки, желтые заметки)
- Оператор открывает MES и запрашивает список новых заказов.
- MES API проверяет кэш (Redis) по ключу orders:new.
- Кэш не содержит данные (cache miss).
- MES API запрашивает данные из MES DB.
- Получает список заказов.
- Сохраняет результат в Redis с TTL=60 секунд и возвращает список оператору.
Или
- Оператор открывает MES и запрашивает список новых заказов.
- MES API проверяет кэш (Redis) по ключу orders:new.
- Кэш  содержит данные.
- Получает список заказов.
**Обновление статуса заказа** (зеленые стелочки и заметки)
- Оператор берёт заказ в работу — отправляет PATCH-запрос.
- MES API обновляет статус в MES DB.
- Инвалидирует кэш для orders:new и orders:in_progress, чтобы при следующем запросе данные обновились.
- Возвращает подтверждение

### Инвалидации кеша

Выбор был между: 

| **Программная (по событию)** |  **Временная (TTL)**| **По ключу** |
|------------------|------------------|----------------------|
|Лучше подходит, потому что обеспечивает **максимальный контроль** над актуальностью данных в критических сценариях.<br><br>1) Позволяет мгновенно инвалидировать кэш при изменении статуса заказа или назначении оператора.<br>2) Гарантирует, что оператор увидит обновлённый список заказов уже при следующем обновлении. |Позволяет сделать **автоматическую очистку кэша** через заданный интервал, что снижает нагрузку на разработчика и предотвращает застой данных.<br><br>Не позволяет сделать мгновенное обновление — данные могут оставаться устаревшими до истечения TTL, что неприемлемо для динамичных сценариев (например, изменение статуса заказа). | Хорошо работает в сочетании с TTL, но **сама по себе не решает задачу полного контроля**. Требует точного знания всех зависимых ключей (например, `orders:new`, `orders:in_progress`), что усложняет поддержку при росте системы. Без TTL может привести к ситуации, когда кэш никогда не обновляется, если событие инвалидации потеряно. |

> Можно комбинировать 2 стратегии **Программная (по событию)** и **Временная (TTL)**
