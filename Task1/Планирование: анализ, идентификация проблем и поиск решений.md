# Анализ

**Онлайн-магазин**

*Стек*: Vue и Java Spring Boot

*Пользователи*: клиенты (заказчик) - Пользователь может сделать заказ, загрузить 3D-модель, работать в 3D-редакторе.

*Функции*: 
  - Создание заказа.
  - Загрузка 3D-модели.
  - Работа в 3D-редакторе.

*Связь с другими сервисами*: Через `Shop API` → `Shop DB` и `3d files storage`

**CRM**

Стек: SPA-приложение, фронтэнд написан на Vue, бэкенд — на Java Spring Boot.

Пользователи: продавцы - Обрабатывают заказ, подтверждают изготовление для пользователя

*Функции*: 
  - Обработка заказов.
  - Подтверждение изготовления.
  - Взаимодействие с клиентом.

*Связь с другими сервисами*: `CRM API` получает сообщения из `Messages Queue` и создаёт заказы и отправляет данные в  `3d files storage`

**MES**

Стек: SPA-приложение, фронтенд написан на React, бэкенд — на C#.
Пользователи: Операторы - берет заказы в работу, изготавливает украшения

*Функции*:
  - Распределение заказов по операторам.
  - Отображение списка заказов (дашборд).
  - Расчёт стоимости изделия на основе 3D-модели.
*Связь с другими сервисами*: `MES API` взаимодействует с `MES DB`, `3d files storage` и `Messages Queue`.

-------------------------------------------------
***Инфраструктура***
Окружения: dev, release и prod. 

***Развертывание***
 - Деплой в dev-окружение осуществляется автоматически после мёрджа пул-реквеста и прохождения юнит-тестов 
 - В release-окружения и в продакшн версию деплоят вручную.


***Маштабируемость***
Приложение микросервисное --> имеются связи между разными сервисами. Расширение приложения не должно вызывать больших проблем.  
Каждый сервис имеет по одному инстансу. Базы данных имеют один инстанс, который работает на запись и на чтение.

# Идентификация проблем

| № | Проблема | Риск | Источник |
|---|---------|------|----------|
| 1 | **Долгий расчёт стоимости в `MES API`** | Пользователи долго ждут, API может упасть, потеря расчёта | Синхронная обработка тяжёлой операции |
| 2 | **Медленная загрузка дашборда в `MES`** | Операторы теряют время, снижается производительность | Высокая нагрузка на `MES DB`, отсутствие кеширования |
| 3 | **Медленная загрузка  `Онлайн-магазина`** | Потеря потенциальных клиентов, упадок репутации | из-за увелечения клиентов отсутствие кеширования |
| 4 | **Задержки в релизах** | Баги и фичи не попадают вовремя, потеря клиентов | Ручной деплой, недостаток автоматизации тестирования |
| 5 | **Несогласованность статусов между `CRM`, `MES`, `Shop`** | Клиенты не видят статус, операторы путаются | Отсутствие единого источника истины, асинхронные события |
| 6 | **Проблемы с очередью (`RabbitMQ`)** | Заказы теряются, задерживаются, "пропадают" | Нет мониторинга |
| 7 | **Сложно отследить "потерю заказа"** | Невозможно быстро диагностировать сбой | Нет централизованного логирования и трейсинга |



# Поиск решений

**Оптимизация расчёта стоимости**
(решение для пункт 1)
MES API можно разделить.

`MES API будет `
 * Принимать 3D-файл.
 * Возвращать task_id.
 * Ставить задачу в RabbitMQ.
 * Синхронизация с MES DB

Создать отдельный сервис (например, CostCalculator) для расчета стоимости по 3d модели — читает очередь и выполняет расчёт.
 `CostCalculator Worker`
  - Потребляет задачи из очереди.
  - Выполняет расчёт (с доступом к `3d files storage`).
  - Сохраняет результат в `MES DB`.
  - Отправляет уведомление (через очередь или WebSocket).

**Репликация БД и кеширование**

(решение для пунктов 2 и 3)
Для оптимизации загрузки сервисов и удобной работы с ними нужно настроить репликации БД (MES DB, SHOP DB). И определить реплики для записи и чтения, на каждую из реплик добавить подходящее кеширование. На реплику чтения можно применить паттер - Cache-Aside + инвалидация кеша при записи. А на реплику записи - Write-Through(так как система работает с заказыми и хочется исключить несогласованность или потерю данных в случае отказа redis)

Кешировать такие данные как: 
 * списки заказов 
 * детали заказа
 * результаты расчёта стоимости

(для пункта 1) - кешируем уже посчитанные 3d модели.


**Добавление инстансов + Load Balancer.**

(для быстрой работы приложений и отказоустойчивости, и должно помочь для пунктов 5,6 )

API GATEWAY для направления запросов к инстансам нашего приложения. 
Разворот инстансов - для повышение быстродействия сервисов и отказоустойчивости

**Нанять сотрудников** 
(для пункта 3)

Нанять старшего QA инденера, у которого есть опыт написания авто-тестов, чтобы он делился опытом с текущим сотрудников + ускорение тестирования релизов.

**Донастройка окружения**
(для пункта 3)
Для прода и dev окружения-> добавить автоматический деплой если релиз прошел тестирование успешно.

**Добавление систем мониторинга**
(для пункта 7)
- Добавить tracing (например, Jaeger):
  - Отслеживание жизненного цикла заказа от API до БД.
- Мониторинг:
  - Prometheus + Grafana: метрики API, очередей, БД.
  - Алерты: при росте очереди, падении сервиса.

# Инициативы в порядке приоритета

**Какой вы видите целевую архитектуру через полгода?**
Цель через 6 месяцев — система, которая:

- Не теряет заказы.
- Справляется с ростом нагрузки.
- Позволяет быстро диагностировать сбои.
- Поддерживает масштабирование.

**Инициативы в порядке приоритета**

1) Оптимизация расчёта стоимост
2) Репликация БД и кеширование 
3) Добавление инстансов + Load Balancer
4) Добавление систем мониторинга 
5) Донастройка окружения

**Выбор трех пунктов**
1) Добавление инстансов + Load Balancer
2) Настроить read-реплики и кеширование для БД
3) Оптимизация расчёта стоимости (выделение сервиса CostCalculator Worker)

Выбраны эти три пункта так как, заказы растут, и нам важно обеспечить быстродействие и отказоустойчивость системы. А также не потерять доверие клиентов + обеспечить удобную работу в наших системах для своих сотрудников.
